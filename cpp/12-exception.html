第 12 课 异常处理：把「出错了」和「算完了」分开

预计 30 分钟·约 6,157 字·C++

一个除法函数遇到除数为 0 怎么办？最直接的想法是返回一个特殊值，比如 -1，让调用方自己判断。这个约定能工作，前提是每个调用点都真的检查了。现实是，写的时候想着「这里不会出错」，过两天就忘了，编译器也不会提醒你。

异常换了个思路：出错时直接中断正常流程，一层层往外找能处理它的人。找不到，程序就终止。它不能保证你处理错误，但能保证错误不会被无声无息地吞掉。

12.1 用返回值报错，为什么靠不住#

先看一个典型的错误码写法。第三个参数是引用，函数把算好的结果写回给调用方。

C++
#include <iostream>

int divide(int a, int b, int& result) {
    if (b == 0) {
        return -1;
    }
    result = a / b;
    return 0;
}

int main() {
    int r = 0;
    if (divide(10, 0, r) != 0) {
        std::cout << "除法失败\n";
    }

    divide(10, 0, r);
    std::cout << "r = " << r << "\n";
}
运行结果
除法失败
r = 0

第一次调用记得检查，第二次忘了，编译器一声不吭，程序带着错误的结果继续往下跑。这种 bug 最难查，因为它不崩，只是数字不对。

错误码还有几个结构性问题。返回值和错误状态挤在同一个 int 里，-1 到底是「除数为零」还是「结果本来就是 -1」，调用方分不清。每层函数都得把错误码原样往上传，中间漏一层就断了。构造函数更麻烦，它没有返回值，想报错只能靠一个 ok() 成员让调用方自己去查。

异常把这两件事分开：正常路径 return 结果，出错路径 throw 一个对象。

12.2 throw 和 catch：错误直接跳出去#

C++
#include <iostream>
#include <stdexcept>

int divide(int a, int b) {
    if (b == 0) {
        throw std::runtime_error("除数不能为 0");
    }
    return a / b;
}

int main() {
    try {
        std::cout << divide(10, 2) << "\n";
        std::cout << divide(10, 0) << "\n";
        std::cout << "这一行不会执行\n";
    } catch (const std::runtime_error& e) {
        std::cout << "捕获：" << e.what() << "\n";
    }
    std::cout << "程序继续\n";
}
运行结果
5
捕获：除数不能为 0
程序继续

throw 会创建一个异常对象，然后立刻中断当前函数。divide(10, 0) 后面的 std::cout 不会执行，divide 里的 return 也不会执行。控制流开始沿着调用栈往外找 catch，找到了就跳进去，找不到就调用 std::terminate 结束程序。std::runtime_error 是标准库现成的异常类型，构造时给一句描述，what() 就能把它取回来。

catch 的参数写成 const std::runtime_error&，有两个原因。按引用是为了不拷贝异常对象；加 const 是因为你通常只读它，而且这样能接住临时对象。按值捕获会发生切片：如果实际抛出的是 runtime_error 的派生类，按值 catch 会把它切成基类，派生类里多出来的信息全丢。这就是第 9 课 继承与多态：让不同的东西说同一种话 讲过的对象切片。

catch 可以写多个，按从上到下的顺序匹配，第一个匹配的生效。所以派生类的 catch 必须写在基类前面，否则永远轮不到它。

throw 的对象可以是任何能拷贝的类型，但别真乱扔。抛 int、抛字符串、抛裸指针，调用方根本不知道要 catch 什么类型，也没法从异常里读出有用的信息。标准做法是抛一个继承自 std::exception 的类。

12.3 栈展开：局部对象为什么会被收拾干净#

每次函数调用，运行时都会给它留一小块地方放参数和局部变量，这些小块叠起来叫调用栈。异常最容易被低估的地方，就是它退出函数时对这些局部对象的处理。

C++
#include <iostream>
#include <stdexcept>

class Guard {
public:
    explicit Guard(const char* name) : name_(name) {
        std::cout << "进入 " << name_ << "\n";
    }
    ~Guard() {
        std::cout << "离开 " << name_ << "\n";
    }

private:
    const char* name_;
};

void inner() {
    Guard g("inner");
    throw std::runtime_error("inner 出错");
}

void outer() {
    Guard g("outer");
    inner();
    std::cout << "outer 的后续代码\n";
}

int main() {
    try {
        outer();
    } catch (const std::exception& e) {
        std::cout << "main 捕获：" << e.what() << "\n";
    }
}
运行结果
进入 outer
进入 inner
离开 inner
离开 outer
main 捕获：inner 出错

throw 之后，inner 的那块栈空间被销毁，局部对象 g 的析构函数被调用，打印「离开 inner」。然后异常传播到 outer，outer 也没有 catch，于是它的栈空间也被销毁，g 析构，打印「离开 outer」。最后 main 的 catch 接住它。

这个过程叫栈展开。它保证了一件事：只要资源由局部对象持有，无论函数是正常返回还是被异常打断，析构函数都会跑。第 5 课 构造、析构与 RAII 里的 FileGuard、std::vector、std::string 全都受益于此。

反过来，如果你在函数里裸写 new，throw 之前没 delete，那块内存就漏了，因为没有任何对象的析构函数知道它。这就是为什么 RAII 和异常是一对：异常负责打断，RAII 负责收尾。

★可选对照

学过 C 的同学会眼熟 goto cleanup：所有失败分支跳到同一个标签，在那里统一释放资源。它的问题是每个函数都得手写一遍，中间加一个资源就要改所有分支。没学过 C 可以完全忽略这段，记住上面那句「异常负责打断，RAII 负责收尾」就够了。

12.4 std::exception 与自定义异常#

标准库的异常都继承自 std::exception，它有一个虚函数 what()，返回错误描述。std::runtime_error、std::out_of_range、std::invalid_argument 都是它的派生类。

实际项目里，你通常需要带更多信息的异常：不只是「文件打不开」，还要知道是哪个文件、为什么打不开。做法是继承一个标准异常，把额外信息存成成员。

C++
#include <iostream>
#include <stdexcept>
#include <string>

class FileError : public std::runtime_error {
public:
    FileError(const std::string& path, const std::string& reason)
        : std::runtime_error("文件错误：" + path + "（" + reason + "）"),
          path_(path) {}

    const std::string& path() const { return path_; }

private:
    std::string path_;
};

void openConfig(const std::string& path) {
    if (path != "config.ini") {
        throw FileError(path, "找不到文件");
    }
    std::cout << "打开 " << path << "\n";
}

int main() {
    try {
        openConfig("setting.ini");
    } catch (const FileError& e) {
        std::cout << e.what() << "\n";
        std::cout << "出问题的路径：" << e.path() << "\n";
    } catch (const std::exception& e) {
        std::cout << "其他标准异常：" << e.what() << "\n";
    }
}
运行结果
文件错误：setting.ini（找不到文件）
出问题的路径：setting.ini

FileError 的构造函数把拼好的消息传给基类 std::runtime_error，what() 返回的就是这串文字。自己额外存一个 path_，catch 里可以取出来做更细的处理。

what() 在 std::exception 里是虚函数，所以就算你手里是 const std::exception&，调到的也是派生类写的那份实现。这也是为什么自定义异常最好继承标准异常：外层可以统一用 catch (const std::exception&) 兜底，同时又保留了具体类型的信息。

catch 的顺序体现了继承关系：FileError 的 catch 在前，std::exception 的 catch 在后。反过来写，FileError 会被基类的 catch 先接住，e.path() 就调不到了。编译器不会提醒你这个顺序问题，只能自己记。

自定义异常类要满足两个条件：能拷贝（异常对象在传播过程中会被复制），析构函数不抛异常。继承 std::runtime_error 再加几个 std::string 成员，天然满足。

12.5 捕获之后怎么办#

捕获异常不等于处理完了。常见的三种动作：就地处理、记完日志重新抛出、转换成另一种异常再抛。

C++
#include <iostream>
#include <stdexcept>

void load() {
    try {
        throw std::runtime_error("底层失败");
    } catch (const std::exception& e) {
        std::cout << "记录日志：" << e.what() << "\n";
        throw;
    }
}

int main() {
    try {
        load();
    } catch (const std::exception& e) {
        std::cout << "上层处理：" << e.what() << "\n";
    }
}
运行结果
记录日志：底层失败
上层处理：底层失败

throw; 不带参数，意思是「把当前正在处理的这个异常原样再抛出去」，类型和信息都不变。这一点很关键：写成 throw e; 会按 e 的静态类型复制一份，如果 e 是 const std::exception&，派生类的信息就被切片丢掉了。

catch (...) 能接住所有异常，但它连异常是什么都不知道。它只适合两种场合：在最外层兜底，保证程序不直接崩；或者清理完局部资源后立刻 throw; 重新抛出。用 catch (...) 把异常吞掉、当无事发生，是最糟的写法——问题还在，只是你再也看不到它了。

还有一条原则：能处理的才 catch，处理不了就让它往上走。一个函数如果只是「不想看到异常」而捕获，通常是在制造隐患。

12.6 什么时候不该用异常#

异常不是万能的，有些场景用返回值更合适。

  • 失败是常态、调用方每次都要处理的情况，比如解析用户输入、查表没找到
  • 对性能极其敏感的代码：不抛异常时几乎没额外开销，可一旦抛出，构造异常对象和栈展开都不便宜
  • 编译时关闭了异常的环境，比如某些嵌入式工具链和游戏主机
C++
#include <cstddef>
#include <iostream>
#include <stdexcept>
#include <string>

bool parseInt(const std::string& text, int& out) {
    try {
        std::size_t used = 0;
        int value = std::stoi(text, &used);
        if (used != text.size()) {
            return false;
        }
        out = value;
        return true;
    } catch (const std::exception&) {
        return false;
    }
}

int main() {
    int n = 0;
    std::cout << parseInt("42", n) << " " << n << "\n";
    std::cout << parseInt("4x", n) << " " << n << "\n";
}
运行结果
1 42
0 42

std::stoi 把字符串转成整数，输入非法时会抛异常；但「用户输入了非数字」是可预期的失败，不该让整个程序进入异常流程。所以在 parseInt 这个边界上把它接住，转成 bool 返回。注意失败时 out 没有被改，仍然是 42——这是有意的，调用方可以据此判断结果是否有效。

noexcept 用来标记一个函数「保证不抛异常」。它不是建议，是承诺：如果标了 noexcept 的函数真的抛了，程序直接 std::terminate，没有商量余地。析构函数默认就是 noexcept，所以更不要在析构里 throw。移动构造函数也常标 noexcept，原因第 14 课会讲。

一句话总结：异常适合「不该发生、发生了也没法就地解决」的错误；可预期的失败用返回值；析构函数和 noexcept 函数里，永远不要抛。

◆小结
  • throw 立刻中断当前函数，沿调用栈找 catch，找不到就 terminate
  • catch 用 const 异常类型&，避免拷贝和切片；派生类的 catch 写在基类前面
  • 栈展开会析构所有局部对象，这是 RAII 能和异常配合的根本原因
  • 自定义异常继承 std::runtime_error，用 what() 给出信息，用成员携带细节
  • throw; 原样重抛；可预期的失败用返回值；析构函数和 noexcept 函数里不要抛
✎练习
  1. 把 12.1 的 divide 改成除数为 0 时抛 std::invalid_argument，在 main 里捕获并打印 what()。再写一个不捕获的版本，观察程序如何终止。
  2. 写一个 Timer 类，构造时打印「开始」，析构时打印「结束」。在它作用域内抛异常，验证析构仍然执行，并说明栈展开的顺序。
  3. 自定义 AgeError 继承 std::runtime_error，保存非法的年龄值，提供 age() 成员。构造一个年龄为 -1 的对象触发它，在 catch 里同时打印 what() 和 age()。
  4. 下面四种写法各有问题，分别说明后果：catch (std::exception e) 按值捕获；catch (...) 里什么都不做；在析构函数里 throw；在 catch 里写 throw e; 而不是 throw;。
