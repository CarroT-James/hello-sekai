第 16 课 项目组织与调试：把代码拆成多个文件

预计 35 分钟·约 5,715 字·C++

你之前写的程序都在一个 main.cpp 里。几十行还行，几百行就开始翻半天；两个人一起写更是灾难。这一课把代码拆成多个文件，再把编译、链接和 gdb 讲一遍——那些报错信息终于能看懂了。

先记住一句话：编译错误是语法和类型的问题，链接错误是「找不到定义」的问题。 分清这两类，一半的报错就不用猜了。

16.1 一个文件写不下的时候#

一个 .cpp 文件在编译器眼里是一个翻译单元，它会被单独编译成一个目标文件 .o，最后再由链接器把多个 .o 拼成可执行文件。拆文件不是为了好看，而是让编译器一次只处理一小块，也让不同的人能同时改不同的文件。

TEXT
project/
├── main.cpp
├── student.h
└── student.cpp

student.h 放类的声明，student.cpp 放成员函数的定义，main.cpp 只负责调用。头文件不是单独编译的，它会被 #include 原样粘进包含它的 .cpp 里。这一点很重要：头文件写错了，报错算在包含它的那个源文件的编译过程里，错误位置通常指向头文件的行号。

拆文件还有个好处是增量编译。改 student.cpp 只需要重新编译它，再链接一次，不用把整个项目从头编一遍。项目大了之后，这是几分钟和几十分钟的差别。

16.2 头文件：只放声明#

student.h 里只写「有什么」，不写「怎么做」。

C++
#ifndef STUDENT_H
#define STUDENT_H

#include <string>
#include <vector>

class Student {
public:
    Student(std::string name, int id);

    const std::string& name() const;
    int id() const;
    void addScore(int score);
    double average() const;

private:
    std::string name_;
    int id_;
    std::vector<int> scores_;
};

#endif

开头的 #ifndef STUDENT_H、#define STUDENT_H 和结尾的 #endif 叫头文件保护（include guard）。它的作用是：同一个头文件在同一个源文件里被包含两次时，第二次的内容会被跳过。没有它，student.h 被两个头文件分别包含，最后在同一个 .cpp 里出现两次，类就被定义两次，编译器报 redefinition of 'Student'。

#pragma once 是更短的写法，几乎所有现代编译器都支持，但它不在 C++ 标准里。教学项目和跨平台代码用 include guard 最稳，两者选一个，别在同一个文件里混用。

头文件里不要写 using namespace std;。头文件会被很多源文件包含，这一行会把整个 std 塞进每个包含者的全局命名空间，迟早撞名。写 std::string 不丢人，多敲五个字符，省掉一下午的排查。

也不要在头文件里定义普通函数或全局变量。头文件被两个 .cpp 包含，函数就被定义两次，链接器会报 multiple definition。例外是 inline 函数和模板，它们允许多处定义。第 11 课 模板与泛型：写一遍，适配所有类型 里模板定义必须放头文件，就属于这种例外。

16.3 实现文件与 main#

student.cpp 包含自己的头文件，然后逐个实现声明过的成员函数。

C++
#include "student.h"

#include <numeric>
#include <utility>

Student::Student(std::string name, int id)
    : name_(std::move(name)), id_(id) {}

const std::string& Student::name() const {
    return name_;
}

int Student::id() const {
    return id_;
}

void Student::addScore(int score) {
    scores_.push_back(score);
}

double Student::average() const {
    if (scores_.empty()) {
        return 0.0;
    }
    return std::accumulate(scores_.begin(), scores_.end(), 0.0) /
           scores_.size();
}

每个成员函数前面都要加 Student::，告诉编译器「这是 Student 的成员」。漏掉它会变成另一个普通函数，带 const 的还会直接编译报错，链接时也仍然找不到 Student::average() 的定义。参数列表和返回类型必须和头文件完全一致，const 也不能少——double average() 和 double average() const 是两个不同的函数。

构造函数用 std::move 接管传进来的 string，省掉一次拷贝（第 14 课 智能指针与移动语义：让「谁负责释放」写进类型 讲过它）。std::accumulate 的初始值写 0.0 而不是 0，保证累加在 double 里进行；写 0 的话整数除法会把 87.5 截成 87。

main.cpp 只做一件事：用这个类。

C++
#include "student.h"

#include <iostream>

int main() {
    Student s("小林", 2024001);
    s.addScore(90);
    s.addScore(85);
    std::cout << s.name() << " " << s.id() << " " << s.average() << "\n";
}
运行结果
小林 2024001 87.5

注意 main.cpp 只包含了 student.h，没有包含 student.cpp。源文件不是用来包含的，它们由编译器分别编译，再由链接器拼起来。#include "student.cpp" 是一种看起来很聪明、实际上会制造重复定义的写法，别用。

16.4 用 g++ 编译与链接#

一条命令就能把三个文件编成可执行文件。

Shell
# 一步到位：编译 + 链接
g++ -std=c++11 -Wall -Wextra -g main.cpp student.cpp -o app
./app

# 分步：先编译成目标文件，再链接
g++ -std=c++11 -c student.cpp -o student.o
g++ -std=c++11 -c main.cpp -o main.o
g++ main.o student.o -o app

-std=c++11 指定标准。本课和前面几课的代码都按 C++11 写，GCC 4.9 完全支持；不写这个参数，老编译器会按更早的标准处理，auto、override、nullptr 这些都可能报错。-Wall -Wextra 打开常用警告，新手至少把这两个加上：警告不是噪音，很多未定义行为在变成崩溃之前，会先以警告的形式出现。-g 生成调试信息，后面用 gdb 必须加。-O2 是发布时的优化，调试阶段先别开，优化会把变量和行号改得面目全非，断点跳来跳去，print 出来的值也可能被优化没。

-c 表示「只编译，不链接」，输出 .o 目标文件。最后一步把所有 .o 交给链接器，-o app 指定输出文件名。编译顺序不重要，链接时目标文件的顺序在大多数情况下也不重要，但库的顺序有讲究，初学阶段先不用管。

Windows 上用 MinGW 的话命令一样，输出是 app.exe，运行时写 .\app.exe。在 Dev-C++ 5.11 里，先新建一个 Console Application 项目，把三个文件都加进项目（右键项目 → Add），再到「项目属性 → 编译器」的「编译时加入以下命令」里填 -std=c++11，最后按 F11 编译运行。一定要建项目，别把三个文件当三个独立源文件分别编译——那样链接器不会把它们拼在一起。

16.5 常见链接错误：undefined reference#

编译通过、链接失败，最常见的报错长这样：

TEXT
main.cpp:(.text+0x2a): undefined reference to `Student::average() const'
collect2: error: ld returned 1 exit status

翻译一下：main.cpp 调用了 Student::average()，编译时只看到声明，就先记了一笔；链接器去找它的定义，所有 .o 里都没有，于是报错。

原因通常有三种。第一种，student.cpp 没参与编译或链接，比如命令里漏了它。第二种，定义写在了另一个没被链接的 .cpp 里，或者类名、命名空间写错，实际定义的是另一个类的成员。第三种，函数只在头文件里声明了，压根没写实现。

另一类错误是 multiple definition of ...，意思是同一个函数被定义了多次。常见原因是把函数定义写进了头文件，被多个 .cpp 包含；或者 #include 了 .cpp 文件；或者把全局变量的定义放在了头文件里（定义只能有一份，头文件却会被粘进很多份）。看到这个错误，先查「这个定义是不是出现在了头文件里」。

还有一类是缺库：报错里的符号是某个库提供的，链接时没告诉编译器去连它。这时候先看符号属于哪个库，再查对应的链接选项，比如多线程要加 -pthread，某些平台上用数学函数要加 -lm。

16.6 用 gdb 找出崩溃的那一行#

程序能编译、能链接，但一跑就崩，这时候该 gdb 上场了。前提是编译时加了 -g。

TEXT
$ g++ -std=c++11 -g main.cpp student.cpp -o app
$ gdb ./app
(gdb) break main
Breakpoint 1 at 0x...: file main.cpp, line 5.
(gdb) run
(gdb) next
(gdb) print s.id()
$1 = 2024001
(gdb) continue

break main 在 main 函数入口下断点，run 启动程序，next 执行下一行（遇到函数调用不进去），step 则会进入函数内部。print s.id() 可以查看变量，甚至调用成员函数。continue 让程序继续跑到下一个断点或者结束。

崩溃时 gdb 会停下来，这时最有用的命令是 bt（backtrace），它打印调用栈，从崩溃的位置一路往上，告诉你「哪个函数调了哪个函数」。配合 frame N 切到某一层、info locals 看局部变量、list 看当前行附近的源码，基本就能定位到出问题的变量。

除了崩溃，gdb 还能查「结果不对」：在可疑的位置下断点，print 出中间值，和手算的对一遍。这比到处插 cout 干净，删的时候也不会漏。

Windows 上 MinGW 自带 gdb，命令一样。Dev-C++ 里更简单：在行号左边点一下下断点，按 F5 开始调试，鼠标悬停就能看变量的值——底下用的是同一套东西。

16.7 include 顺序与项目清单#

#include 的顺序建议固定成三组，组间空一行：自己的头文件放最前，标准库头文件放中间（按字母排），第三方库放最后。

自己的头文件放最前，是为了验证它是自包含的：如果 student.h 用了 std::string 却没包含 <string>，把它放在最前面，编译会立刻报错；放在最后面，可能被前面某个头文件顺带包含了，问题就被藏起来，换一个包含顺序又炸。

项目结构可以从简：src/ 放 .cpp，include/ 放 .h，build/ 放编译产物；每个头文件都能单独编译，不依赖「先包含别的头文件」；编译命令写进 Makefile 或 CMakeLists.txt，别靠记忆；提交代码前用 -Wall -Wextra 从头编一遍，把警告清掉；出问题先分清是编译错误、链接错误还是运行时错误，再决定看编译器、看链接命令，还是上 gdb。

这几步听起来琐碎，但它们是把「能跑」变成「能维护」的分界线。你不需要一次全做到，先从「拆成三个文件、一条命令编译、崩溃时看 bt」开始。

◆小结
  • .cpp 分别编译成 .o，再由链接器拼成可执行文件；头文件是被 #include 粘进去的
  • 头文件只放声明，加 include guard；普通函数定义、全局变量、using namespace 都不要放
  • -std=c++11 -Wall -Wextra -g 是日常编译的起步配置，-c 只编译不链接
  • undefined reference 是找不到定义，multiple definition 是定义重复，先查源文件清单和头文件
  • gdb 的 break、run、next、print、bt 五个命令，足够定位大多数崩溃
✎练习
  1. 把 Student 拆成 student.h、student.cpp、main.cpp 三个文件，用一条 g++ 命令编译运行；再从命令里去掉 student.cpp，记录链接错误并解释。
  2. 在 student.h 里加一个普通函数定义（不带 inline），让两个 .cpp 都包含它，观察 multiple definition 错误；再改成 inline 或挪进 .cpp，验证错误消失。
  3. 写一个会解引用空指针的小程序，用 -g 编译，在 gdb 里 run 到崩溃，执行 bt 和 frame 0，指出崩溃发生在哪一行、哪个函数。
  4. 为一个多文件小项目安排 #include 顺序，说明为什么自己的头文件要放最前面；再解释 include guard 和 #pragma once 的区别与取舍。
