第 6 课 开发环境与调试

预计 33 分钟·约 5,009 字·计算机基础

代码跑不对的时候，多数人的第一反应是盯着屏幕看，指望突然发现哪里错了。看十分钟，改一个字符，再跑一次，还是错。

调试不是玄学，是一套可以照着走的流程：读报错、缩小范围、看中间值、验证假设。这一课把工具和流程都过一遍。

6.1 编辑器、编译器、IDE，别搞混#

这三样东西经常被混着叫，其实分工很清楚。

编辑器只负责让你打字。记事本、VS Code、Sublime 都是编辑器。它认识语法、能高亮、能补全，但它不会把你写的 C 变成能跑的程序。

编译器负责翻译。gcc、clang、MSVC 是 C 的编译器；Python 那边对应的是解释器，它一边读一边执行，没有独立的「编译成 exe」那一步。

IDE（集成开发环境）把编辑器、编译器、调试器、项目管理打包在一起，点一个按钮全给你串起来。Dev-C++、Visual Studio、CLion 都是 IDE。

所以「VS Code 装好了怎么还是跑不了 C」这个问题的答案是：VS Code 只是编辑器，你还得装 gcc，再装个 C/C++ 扩展把它俩接起来。而 Dev-C++ 里已经包含了 gcc，所以开箱能用。

工具是什么典型代表
编辑器打字的地方VS Code、Sublime、Vim
编译器把 C 变成机器码gcc、clang、MSVC
调试器让程序停在某一行给你看gdb、lldb、VS 调试器
IDE上面三样的打包Dev-C++、Visual Studio、CLion

这张表值得记住，因为报错的时候你要能判断是谁在说话。error: expected ';' 是编译器说的，Segmentation fault 是操作系统说的，ModuleNotFoundError 是解释器说的。谁说的，决定了你该改什么。

★命令行编译其实更省事

Dev-C++ 点按钮很方便，但学会这两行，你在任何一台机器上都能干活：gcc hello.c -o hello 编译，./hello 运行。加上 -Wall -Wextra -g 是标配：前两个打开警告，-g 保留调试信息，后面用 gdb 全靠它。养成写全的习惯，别等出错才想起加。

6.2 读报错：只看第一个 error#

下面这个程序有两个 bug，一个编译器能抓，一个抓不到：

C
#include <stdio.h>

int main() {
    int scores[3] = {80, 90, 70}
    int i;
    int sum = 0;

    for (i = 0; i <= 3; i++) {
        sum += scores[i];
    }

    printf("平均分：%d\n", sum / 3);
    return 0;
}

gcc -Wall -Wextra bug.c -o bug 会吐出：

运行结果
bug.c: In function 'main':
bug.c:4:34: error: expected ';' before 'int'
    4 |     int scores[3] = {80, 90, 70}
      |                                  ^
      |                                  ;
bug.c:8:18: error: 'scores' undeclared (first use in this function)

第一个错在 4 行 34 列，缺分号，而且贴心地告诉你要补什么。第二个错是第一个的连锁反应——编译器处理声明失败，后面就不认识 scores 了。

读报错的三条规矩：

  • 从上往下，只看第一个 error，改完重新编译
  • 行号和列号是「编译器卡住的位置」，真正的问题常在它的前一行或前一个符号
  • 警告不要无视。-Wall 报的 unused variable、comparison between signed and unsigned 里藏着真 bug

分号补上之后，程序能编过了，但结果还是错。这就是第二个 bug：i <= 3 会访问 scores[3]，而数组只有 0、1、2 三个元素。

越界读通常不会崩。它只是把数组后面那块内存里的垃圾读出来，加进 sum。所以程序照跑，结果离谱。这类 bug 编译器抓不到，只能靠调试。

6.3 最土的调试法：printf 插桩#

别小看它。全世界大部分 bug 是被 printf 找出来的，包括在几万行的项目里。

思路是：在怀疑的地方把中间值打出来，看它跟你想的一不一样。第一次不一样的位置，就是 bug 所在。

C
#include <stdio.h>

int main() {
    int scores[3] = {80, 90, 70};
    int i;
    int sum = 0;

    for (i = 0; i <= 3; i++) {
        printf("循环 i=%d，scores[%d]=%d，累加前 sum=%d\n",
               i, i, scores[i], sum);
        sum += scores[i];
    }

    printf("总和 %d，平均 %d\n", sum, sum / 3);
    return 0;
}
运行结果
循环 i=0，scores[0]=80，累加前 sum=0
循环 i=1，scores[1]=90，累加前 sum=80
循环 i=2，scores[2]=70，累加前 sum=170
循环 i=3，scores[3]=32764，累加前 sum=240
总和 33004，平均 11001

一眼就能看出问题：循环跑到 i=3 了，而且 scores[3] 是个莫名其妙的大数。那个 32764 是内存里的垃圾值，每次运行都可能不同。

普通 printf 调试有两个毛病：输出一多就糊成一片，以及改代码本身可能引入新 bug。所以有条纪律：用完删掉，或者包在 #ifdef DEBUG 里。

C
#ifdef DEBUG
    printf("i=%d sum=%d\n", i, sum);
#endif

编译时加 -DDEBUG 才会输出，不加就当作不存在。这个习惯比手工删注释靠谱。

另一个技巧是二分定位：不确定错在哪，就在中间插一句打印，看前半段对不对，然后砍掉一半范围。一百行代码，七次就能定位到一行。

6.4 断点：让程序停下来给你看#

printf 能看到值，但看不到「程序现在走到哪、调用链是什么」。断点补上这一块。命令行不太熟的话，先扫一眼 第 4 课 命令行与 Linux 基础。

先把上面那个分号补上，让程序能编过，然后用 -g 编译，让可执行文件带上行号信息：

Shell
gcc -g -Wall bug.c -o bug

然后进 gdb（Windows 上的 MinGW 一般也带 gdb，没有就装 MSYS2）：

TEXT
$ gdb ./bug
(gdb) break 8
Breakpoint 1 at 0x1155: file bug.c, line 8.
(gdb) run
Breakpoint 1, main () at bug.c:8
8           for (i = 0; i <= 3; i++) {
(gdb) next
9               sum += scores[i];
(gdb) print i
$1 = 0
(gdb) next
8           for (i = 0; i <= 3; i++) {
(gdb) print sum
$2 = 80
(gdb) continue

七个命令足够应付初学阶段：

  • break 行号 在指定行设断点，也可以 break 函数名
  • run 开始跑，撞到断点就停
  • next 执行一行，不进函数内部
  • step 执行一行，会进函数内部
  • print 变量 看当前值，可以写表达式，比如 print scores[3]
  • bt 打印调用栈，看是谁调用了当前函数
  • continue 继续跑到下一个断点

next 和 step 的区别是新手最常问的：next 把函数调用当成一步走完，step 会钻进去。怀疑函数内部有问题时用 step，否则用 next。

觉得命令行太硬，就用 VS Code：装 C/C++ 扩展，在行号左边点一下出现红点，按 F5，左边栏能看到变量值和调用栈，鼠标悬停就能看值。本质上是同一套东西，只是套了个界面。

▲常见错误

断点明明设了却不停。多半是没加 -g，或者改了代码没重新编译，或者断点打在了空行、注释行、被优化掉的代码上。还有一种是程序在断点之前就崩了——那说明 bug 更早，往前挪断点。

6.5 崩溃现场：段错误到底是谁干的#

Segmentation fault 是最常见的崩溃，意思是「你访问了不该访问的内存」。操作系统发现越界，直接终止进程，不给你解释的机会。

两个最小复现：

C
#include <stdio.h>

int main() {
    int *p = NULL;
    printf("还没崩\n");
    printf("%d\n", *p);    /* 解引用空指针 */
    printf("这句不会执行\n");
    return 0;
}
运行结果
还没崩
Segmentation fault (core dumped)

最后那句没打印，说明崩在中间那行。输出停在哪，bug 就在下一行，这是最快的一条线索。

Windows 上你看到的不是这句话，而是一个弹窗或者退出码 0xC0000005——访问冲突。数字不同，原因一样。

第二种更隐蔽：栈溢出。

C
int f(int n) {
    return f(n + 1);    /* 没有终止条件 */
}

每调用一次就压一层栈帧，栈只有几 MB，压满之后程序直接崩，报 stack overflow 或者段错误。写递归忘了写出口，就是这个结果。

第三种最坑：释放后使用。free(p) 之后又去读 p，那块内存可能已经分给别人了，读到什么全看运气。这时候程序可能当场崩，也可能跑一万次才崩一次。

查这类问题，gdb 的 bt 是救命稻草——崩溃时敲 bt，它会把调用链打出来，告诉你崩在哪个函数的哪一行、是谁调用的。

6.6 一张速查表，和一套流程#

把常见报错抄下来，下次遇到了先查表，别急着改代码。

报错真实含义先查什么
expected ';' before ...上一行少分号上一行行尾
undeclared (first use in this function)变量没声明或拼错拼写、作用域
implicit declaration of function用了没声明的函数有没有 #include 对应头文件
undefined reference to ...链接时找不到定义源文件有没有加进编译命令
Segmentation fault访问了非法内存空指针、越界、释放后使用
warning: unused variable声明了没用是不是漏写了要用的地方
warning: comparison between signed and unsigned有符号和无符号混着比统一类型，小心负数被当成大正数

然后是一套可以固定下来的流程：

  1. 先让它编过，只看第一个 error，一个一个消
  2. 把警告清干净，警告里常有真 bug
  3. 结果不对，就在关键位置打印中间值，找出第一个和预期不符的地方
  4. 找不到就用二分法缩小范围，或者上断点看调用栈
  5. 崩了就先看输出停在哪一行，再用 bt 看是谁调的
  6. 修完之后，把刚才那个输入再跑一遍，确认真的好了

第 6 步最容易被跳过。改完能跑不等于修好了，得用当初触发 bug 的那个输入验证一次。

◆小结
  • 编辑器只负责打字，编译器负责翻译，调试器负责让程序停下来，IDE 把三样打包
  • 编译固定用 gcc -Wall -Wextra -g，警告要清，-g 是调试的前提
  • 读报错只看第一个 error，改完就重编；行号是编译器卡住的位置，问题常在前一行
  • printf 插桩找第一个和预期不符的值；断点用 break、run、next/step、print，再加 bt 看调用栈
  • 崩溃先看输出停在哪，停住的下一行就是案发现场
✎练习
  1. 把第 6.2 节的程序改对（修分号、修循环条件、修整数除法），让平均分输出 80.00，用 %.2f 输出。
  2. 故意写一个数组越界写的程序，观察它是当场崩、还是悄悄改掉别的变量，用 printf 打印可疑变量的地址验证你的猜测。
  3. 用 gdb 在 for 循环那一行设断点，逐次 print i 和 print sum，把每一次的值记下来，和 printf 版本的输出对照。
  4. 找一段你以前写错的代码，用本课的六步流程重走一遍，写下每一步你看到了什么、下一步据此做了什么。
