第 2 课 一个程序是怎么跑起来的

预计 30 分钟·约 5,115 字·计算机基础

你在 Dev-C++ 里按一下 F11，黑窗口闪一下，Hello World 就出来了。看起来是一步，其实是四步：预处理、编译、汇编、链接。跑起来还要再加一步：加载到内存。

菜谱写好不代表菜能上桌。中间得有人备料、有人下锅、有人装盘，最后还要有人把盘子端到桌上。这一课把这五个环节一个个拆开。

2.1 四步走：源码到可执行文件#

先写一个最小的程序，故意带上一个全局变量和一个函数调用，让后面每一步都有东西可看。

C
#include <stdio.h>

int counter = 0;

int add(int a, int b) {
    return a + b;
}

int main() {
    counter = add(2, 3);
    printf("counter = %d\n", counter);
    return 0;
}

编译它其实只要一条命令：gcc hello.c -o hello。但这条命令背后替你做了四件事。把每一步单独跑一遍，你就能看见中间产物：

Shell
gcc -E hello.c -o hello.i     # 1. 预处理：展开 #include 和 #define
gcc -S hello.i -o hello.s     # 2. 编译：C 代码翻译成汇编
gcc -c hello.s -o hello.o     # 3. 汇编：汇编翻译成机器码（目标文件）
gcc hello.o -o hello          # 4. 链接：把用到的库拼进来

ls -l hello.i hello.s hello.o hello
运行结果
-rw-r--r-- 1 user user   1721 hello.i
-rw-r--r-- 1 user user    512 hello.s
-rw-r--r-- 1 user user   1568 hello.o
-rw-r--r-- 1 user user  16024 hello

体积能说明问题。hello.i 比源文件大得多，因为 #include <stdio.h> 被原地展开了——那个头文件几千行，全贴进来了。hello.s 是汇编，短了。hello.o 是机器码，更短。最后的 hello 突然变回 16 KB，因为链接器把 printf 的实现从 C 库搬了进来。

第 1 步只是文本替换，不检查语法。所以你忘写分号，gcc -E 一点意见都没有，到第 2 步才骂你。

第 2 步的产物长这样，是给 CPU 看的「文本版」机器指令：

TEXT
    .globl  main
main:
    pushq   %rbp
    movq    %rsp, %rbp
    movl    $2, %edi
    movl    $3, %esi
    call    add
    movl    %eax, counter(%rip)
    ...
    call    printf

pushq、movl、call 这些叫指令，%rbp、%eax 叫寄存器——CPU 里面几个极小的存储格子，比内存快得多。你写的 int a, b 在运行时就住在这种格子里，或者住在栈上，编译器替你安排。

这些指令在文件里最终是一串 0 和 1，怎么读它们，第 1 课 进制与编码 讲过。

★为什么要分四步

分开是有好处的。-c 让你可以只编译改过的那个文件，其他 .o 直接复用，大型项目因此才编得动。-E 让你查宏到底展开成了什么。-S 让你看编译器有没有把你的循环优化掉。这些开关平时不用写，但出问题时它们是唯一的窗口。

2.2 编译器在抱怨什么#

改一行，把第 11 行的分号删掉，再加 -Wall 重新编：gcc -Wall -Wextra hello.c -o hello。

运行结果
hello.c: In function 'main':
hello.c:11:23: error: expected ';' before '}' token
   11 |     counter = add(2, 3)
      |                       ^
      |                       ;

读报错的顺序是从上往下、只看第一个 error。后面一连串报错经常是第一个的连锁反应——少一个分号，编译器会把下一行当成上一行的延续，于是整段都「错」了。修完第一个再编一次，往往一半的报错自己就消失了。

报错的格式是固定的三段：文件:行:列、错误类型、原文和箭头。箭头 ^ 指的那个位置就是编译器卡住的地方，注意它经常比真正出错的位置晚一个符号。

-Wall -Wextra 打开警告。警告不是错误，程序照样能生成，但九成的警告背后是货真价实的 bug。养成带 -Wall 编译的习惯，比事后调试省力得多。

▲常见错误

error: expected declaration or statement at end of input 这种报错指向文件末尾，八成是前面某个 { 没配对。编译器一路读到结尾才发现括号不够，它没法告诉你缺在哪，只能告诉你「读到结尾了还没结束」。这时候从后往前数括号比盯着末尾看有用。

2.3 链接器：拼图少了一块#

编译是「一个文件一个文件」做的。每个 .c 单独变成一个 .o，这时候它不知道别的文件里有什么函数——只知道「有个叫 add 的函数，参数是两个 int，返回值是 int」，这信息来自声明。

把调用和定义拆到两个文件里：

C
/* ---------- math_util.c ---------- */
int add(int a, int b) {
    return a + b;
}

/* ---------- main.c ---------- */
#include <stdio.h>

int add(int a, int b);   /* 声明：告诉编译器有这么个函数 */

int main() {
    printf("%d\n", add(2, 3));
    return 0;
}

声明只需要写函数长什么样，定义才写函数干什么。编译器看到声明就放行，具体地址留空，等链接器来填。

现在故意只编 main.c，看链接器怎么抗议：

Shell
gcc -c main.c -o main.o
gcc main.o -o main
运行结果
main.o:main.c:(.text+0x15): undefined reference to `add'
collect2: error: ld returned 1 exit status

undefined reference 是链接错误，不是编译错误。含义很明确：有人用了一个符号，但没人提供它。修法是把定义所在的文件一起编，gcc main.c math_util.c -o main，跑出来是 5。

这两个错误的区别值得记牢。编译错误说「你这句话不合语法」，链接错误说「这句话语法没问题，但它要的东西不存在」。看到 undefined reference 就别再盯语法了，去查三件事：文件有没有加进编译命令、函数名拼错没有（包括大小写）、有没有在 C++ 里忘了 extern "C"。

2.4 可执行文件里装了什么#

生成的 hello 不是纯机器码，它是一个有格式的容器。Linux 上叫 ELF，Windows 上叫 PE（就是 .exe）。

用 size 能看到它内部的几块地：

Shell
size hello
运行结果
   text    data     bss     dec     hex filename
   1520     600       8    2128     850 hello
  • text 是代码段，你的指令都在这儿，只读
  • data 是已初始化的全局变量和静态变量，初始值要原样存在文件里
  • bss 是「值等于 0」的全局变量，不占文件体积，程序启动时统一清零

注意 int counter = 0; 这种写法会被归进 bss 而不是 data——值本来就是 0，没必要在文件里存一遍。所以上面 bss 只有 8 字节、data 却有 600 字节，那 600 字节大部分来自启动代码和链接进来的库，不是你写的变量。感兴趣可以用 objdump -d hello 把反汇编打出来，能看到 main 和你写的代码一一对应，只是全变成了十六进制。

2.5 加载进内存：四块地#

双击程序，操作系统先给它划一块内存，把文件里的内容搬进去，然后跳到入口开始执行。这块内存被分成几段，位置是固定的：

TEXT
高地址
┌──────────────────┐
│   内核空间        │  用户程序碰不到
├──────────────────┤
│   栈 stack       │  局部变量、函数参数、返回地址，向低地址生长
│       ↓          │
│                  │
│       ↑          │
│   堆 heap        │  malloc 出来的东西，向高地址生长
├──────────────────┤
│   bss            │  未初始化的全局变量
├──────────────────┤
│   data           │  已初始化的全局变量
├──────────────────┤
│   text           │  机器指令，只读
└──────────────────┘
低地址

栈和堆是相向生长的。栈从高地址往低处压，堆从低处往高处要，中间那片空白就是它们共用的空间。两个撞上了，就是栈溢出或者内存耗尽。

写个程序把各类变量的地址打出来看看：

C
#include <stdio.h>

int inited = 10;
int uninited;
static int static_var = 20;

void show(const char *name, void *addr) {
    printf("%s：%p\n", name, addr);
}

int main() {
    int local = 1;
    show("main 函数", (void *)main);
    show("已初始化全局", (void *)&inited);
    show("未初始化全局", (void *)&uninited);
    show("静态变量", (void *)&static_var);
    show("局部变量", (void *)&local);
    return 0;
}
运行结果
main 函数：0000000000401550
已初始化全局：0000000000403010
未初始化全局：0000000000403018
静态变量：0000000000403014
局部变量：000000000061FE1C

地址是示意，每次运行都可能不一样，但相对次序是稳定的：代码段最低，全局变量在中间，栈最高。你看到局部变量那个 61FE1C 明显比其他的 40xxxx 大一大截，那就是栈在高地址区。

再调用一个函数，它里面的局部变量地址会比 main 的更小。这就验证了栈是往下长的。

2.6 程序跑起来那一刻#

还有一件事容易误会：main 不是第一个被执行的函数。

真正第一个跑的是启动代码（Linux 上叫 _start，来自 C 运行库）。它干三件事：准备好栈和全局变量、把命令行参数整理好、然后调用 main。main 返回之后，控制权还会回到启动代码，由它调用 exit 把资源收拾干净。所以你 return 0 之后程序还能正常退出，不是魔法。

CPU 执行的时候，只做三件事，循环往复：

  • 取指：按程序计数器（PC）里的地址，从代码段读一条指令
  • 译码：看懂这条指令要干什么，操作数是哪几个寄存器
  • 执行：算，然后把 PC 指向下一条

call 指令会做一件额外的事：把「下一条指令的地址」压进栈，然后跳到函数入口。函数执行完遇到 ret，就从栈里弹出那个地址跳回去。这就是调用栈，也是你能在调试器里看到 main → add → ... 这条调用链的原因。

如果一个函数里再调用自己，栈就会一层层往上叠（其实是往下压）。叠得太深，栈空间用完，程序崩溃——这就是递归写错时那句 stack overflow 的来历。

◆小结
  • 从源码到程序是四步：预处理展开宏和头文件、编译出汇编、汇编出目标文件、链接把符号拼齐
  • undefined reference 是链接错误，说明符号有声明没定义，跟语法无关
  • 可执行文件分代码段、数据段、bss 段；bss 不占文件体积，启动时清零
  • 进程内存里，代码段在低地址，栈在高地址并向下生长，堆从低往高长
  • main 不是第一个执行的函数，启动代码准备好环境才调它；CPU 只做取指、译码、执行，call 把返回地址压栈
✎练习
  1. 对第 2.1 节的 hello.c 分别跑 gcc -E、-S、-c、链接四步，用 wc -l 统计每个中间文件的行数，解释为什么 .i 特别长。
  2. 故意在 main.c 里把 add 拼成 Add，分别用 gcc -c 和完整链接各编一次，记录哪个阶段报错、报错原文是什么。
  3. 写一个程序，打印 main 里一个局部变量和它调用的函数里一个局部变量的地址，验证栈是向下生长的。
  4. 用 size 看一个带 1000 个已初始化数组和 1000 个未初始化数组的程序，比较 data 和 bss 的变化，解释原因。
