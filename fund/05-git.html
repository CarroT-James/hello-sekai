第 5 课 Git 与版本管理

预计 35 分钟·约 5,647 字·计算机基础

写课程论文时你大概见过这种文件名：论文.docx、论文_修改.docx、论文_最终版.docx、论文_最终版_真的最终.docx。

改到第七版，你已经说不清哪一版是交上去的那份了。打游戏的人不会有这个烦恼——存档、读档，想回到哪一步就回到哪一步。Git 干的就是这件事，只不过它管的是代码，而且存档可以无限多、可以分叉、可以和别人合并。

这一课从装好 Git 到解决第一次冲突，全部按顺序走一遍，跟着敲就行。

5.1 三个区域：桌子、文件袋、存档柜#

先建立这个模型，后面所有命令都能对上号。

  • 工作区：你正在编辑的那份文件，就是屏幕上的内容。相当于摊在桌子上的草稿。
  • 暂存区：一个中间层，你挑出「这次想存档的改动」放进去。相当于把要交的作业装进文件袋。
  • 仓库：真正存下来的历史记录，每次提交就是一个不可更改的存档点。

为什么要有中间那一层？因为你可能同时改了三件事——修了个 bug、加了个功能、顺手改了注释。提交时你想把它们分成三个存档，方便以后单独回退。暂存区就是让你挑挑拣拣的地方。

流程永远是：改文件 → git add 放进文件袋 → git commit 存档。

5.2 装好，配置，建仓库#

Windows 去 git-scm.com 下安装包，一路下一步。装完在开始菜单找到 Git Bash，那是一个自带命令行的窗口。命令行的基本操作在 第 4 课 命令行与 Linux 基础 里讲过，没看过也不影响这一课，照着敲就行。

第一次用要先报名字，Git 会把作者信息写进每个存档：

Shell
git config --global user.name "你的名字"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main

mkdir git-demo
cd git-demo
git init
git status
运行结果
Initialized empty Git repository in /home/you/git-demo/.git/
On branch main

No commits yet

nothing to commit (create/copy files and use "git add" to track)

git init 干的事就是在当前目录建一个隐藏的 .git 文件夹，所有历史、分支、配置都在里面。删掉 .git，这个目录就变回一个普通文件夹，历史全没了。这一点很重要：备份项目时别只拷代码，.git 才是精华。

init.defaultBranch main 只是把默认分支名从 master 改成 main。现在 GitHub 默认也叫 main，两边对上省事。

git status 是你用得最多的命令。任何时候不知道自己在什么状态，敲它就对了。它会告诉你哪些文件改了、哪些已经放进文件袋、下一步该干什么。

5.3 第一次提交#

新建一个文件，然后看状态怎么变：

Shell
printf "# 我的笔记\n\n第一行\n" > notes.md
git status
git add notes.md
git status
git commit -m "添加笔记文件"
git log --oneline
运行结果
Untracked files:
        notes.md

Changes to be committed:
        new file:   notes.md

[main (root-commit) 8f3c1a2] 添加笔记文件
 1 file changed, 3 insertions(+)
8f3c1a2 添加笔记文件

状态从 Untracked（Git 不认识这个文件）变成 Changes to be committed（已放进文件袋），提交之后就有了第一条历史。

git log --oneline 每行一条存档，前面那串 8f3c1a2 是提交编号，你机器上的一定不一样。它是根据内容算出来的哈希值，全球唯一。

-m 后面的说明文字要认真写。三个月后的你会感谢现在的你，而「改了一下」「update」「fix」这种说明等于没写。好的说明长这样：修复登录页在 Safari 下按钮错位。

-m 不写会弹出编辑器让你输入，新手容易卡在 vim 界面里出不来（Esc 然后 :wq 回车可退出）。

5.4 改了什么：diff 与撤销#

改一行（printf "第二行\n" >> notes.md），然后敲 git diff，输出长这样：

运行结果
diff --git a/notes.md b/notes.md
index 3b18e51..a1c9f42 100644
--- a/notes.md
+++ b/notes.md
@@ -1,3 +1,4 @@
 # 我的笔记
 
 第一行
+第二行

+ 是新增，- 是删除。@@ -1,3 +1,4 @@ 的意思是「旧文件从第 1 行起 3 行，新文件从第 1 行起 4 行」。

git diff 比较的是工作区和暂存区。已经 add 过的改动它就不显示了，要看那部分得用 git diff --staged。这个区别新手经常踩：明明改了文件，git diff 却是空的——因为改完已经 add 了，工作区和暂存区一样了。

写错了想撤销，三条命令对应三种「撤」：

Shell
git restore notes.md            # 丢掉工作区里还没 add 的改动（不可恢复）
git restore --staged notes.md   # 把文件从文件袋拿出来，改动还在
git revert 8f3c1a2              # 生成一个新提交，内容是「把那次改动反向做一遍」

前两条是本地操作，restore 丢掉的东西找不回来，用之前想清楚。第三条 revert 是安全的撤销，它不改历史，只是加一个新的反向存档，所以多人协作时用它。

还有一个 git reset --hard 8f3c1a2，直接把整个目录退回到那次提交，之后的改动全没。它确实好用，也确实危险，只在本地、只在确定不要那些改动时用。

▲常见错误

git add 之后反悔，直接改文件再提交，结果提交里混进了没想提交的内容。正确顺序是先 git restore --staged 文件名 把它拿出来，再修改。另外 git commit -a 会跳过暂存区直接提交所有已跟踪文件，看着省事，实际上让你失去「挑拣」的机会，新手先别用。

5.5 分支：开一条平行世界#

到目前只有一条时间线。想试个新功能又怕弄坏能跑的版本，就开一条分支。

分支不是复制一整个目录，它只是一个指向某次提交的指针。所以建分支几乎不花时间和空间，这是 Git 和其他版本工具最大的不同。

Shell
git switch -c feature            # 建一个叫 feature 的分支并切过去
git branch                       # 看所有本地分支，带 * 的是当前分支

printf "这是 feature 分支加的内容\n" >> notes.md
git add notes.md
git commit -m "在 feature 上追加一行"

git switch main                  # 切回 main
cat notes.md                     # 那行像是不见了
git merge feature                # 把 feature 合进 main
cat notes.md                     # 又出现了
git log --oneline --graph

切回 main 之后，文件变回旧内容。不是丢了吗？没有，它在 feature 那条线上。这就是「平行世界」的手感：每条分支各自往前走，互不干扰，需要时再合。

git switch 是 Git 2.23 之后的新写法，老版本里对应的是 git checkout -b，效果一样。两种都见得到，混着用不冲突。

上面这段里 git merge feature 要把 feature 合进当前分支 main，所以必须先在 main 上。如果 main 在分叉之后没动过，这叫快进合并，Git 只是把指针往前挪一下，不产生新提交。如果两边都改过，Git 会做三方合并，那就轮到下一节的冲突了。

5.6 冲突：两个人都改了同一行#

冲突不是错误，是 Git 在说「这两处改动我没法替你决定」。

造一个冲突：在 main 上改 notes.md 的第一行并提交，再切到 feature 改同一行并提交，然后合并。

Shell
git switch main
printf "# 我的笔记（main 改过）\n\n第一行\n" > notes.md
git add notes.md && git commit -m "main 修改标题"
git switch feature
printf "# 我的笔记（feature 改过）\n\n第一行\n" > notes.md
git add notes.md && git commit -m "feature 修改标题"
git switch main
git merge feature
运行结果
Auto-merging notes.md
CONFLICT (content): Merge conflict in notes.md
Automatic merge failed; fix conflicts and then commit the result.

合并会停下来，git status 里显示 both modified: notes.md。打开文件，你会看到：

TEXT
<<<<<<< HEAD
# 我的笔记（main 改过）
=======
# 我的笔记（feature 改过）
>>>>>>> feature

三行标记的含义：<<<<<<< HEAD 到 ======= 之间是当前分支的内容，======= 到 >>>>>>> 之间是合进来的分支的内容。

解决方式就一步：把文件改成你最终想要的样子，然后把三行标记全删掉。注意是删标记，不是删内容。

改完就 git add notes.md，这个动作在这里的含义是「我处理完了」。Git 看到所有冲突文件都被 add，才允许 git commit -m "解决标题冲突，保留双方措辞"。最后 git log --oneline --graph 能看到两条线合成一条。

★冲突其实很少

大部分冲突发生在两个人改同一行。团队里分工清楚、提交勤、每天 pull 一次，冲突会少很多。真正难的不是敲命令，是看懂那两段代码到底哪个对——那需要你和另一个人沟通，Git 帮不了。

5.7 推到远程，拉回本地#

前面的存档全在你自己的硬盘上。硬盘坏了就全没了，也没法协作。所以要有一个远程仓库，GitHub、Gitee 都行。

先在网站上建一个空仓库，拿到地址，然后：

Shell
git remote add origin https://github.com/你的用户名/git-demo.git
git push -u origin main
git remote -v

git clone https://github.com/某个项目/仓库.git   # 拿别人的项目，连历史一起拉

origin 是给这个远程地址起的别名，约定俗成叫这个。-u 是 --set-upstream，把本地 main 和远程 main 绑起来。绑过一次之后，以后只要 git push 和 git pull，不用再写后面那一串。

push 是把本地存档传上去，pull 是把远程的新存档拉下来并合并。日常协作的节奏是：早上 git pull，干活，commit，push。

克隆下来的目录自带完整的 .git，所以 git log 能看到作者几年来的所有提交——这也是为什么很多项目会被人「考古」出十年前的注释。

有些文件不该进仓库：编译产物、临时文件、密码。写一个 .gitignore：

TEXT
build/
*.o
*.exe
__pycache__/
.env

build/ 末尾的斜杠表示只忽略目录，*.o 是通配符。.gitignore 只管还没被跟踪的文件——如果某个文件已经提交过，再加进 .gitignore 是没用的，得先 git rm --cached 文件名。

▲常见错误

把密码、API key、身份证号提交上去，然后 push 到公开仓库。删掉文件再提交一次并不能抹掉历史，别人照样能从旧提交里翻出来。真发生了就立刻去平台作废那个 key，然后重写历史（git filter-repo），别心存侥幸。养成习惯：项目一开始就写好 .gitignore，密钥放环境变量。

◆小结
  • Git 管三个区域：工作区改、暂存区挑、仓库存档；流程是 add 再 commit
  • git status 看状态，git log --oneline 看历史，git diff 看具体改了哪几行
  • git restore 丢工作区改动，git restore --staged 取消暂存，git revert 安全地反向提交
  • 分支只是一个指针，switch -c 建、switch 切、merge 合；冲突就手工改成最终版本、删掉标记、add 再 commit
  • push -u 绑一次远程，之后 push / pull；.gitignore 从一开始就写好
✎练习
  1. 建一个 git-demo 仓库，提交三次有意义的改动，用 git log --oneline 和 git diff HEAD~1 分别看历史和最近一次改动。
  2. 在 main 上改一行不提交，用 git diff 看差异；然后 git add 再 git diff 一次，解释为什么第二次是空的。
  3. 建一个 feature 分支，在两边改同一个文件的同一行并各自提交，合并触发冲突，手工解决后提交，用 --graph 看合并结果。
  4. 给一个已有的项目补一个 .gitignore，忽略 *.exe 和 build/；如果发现 a.exe 已经被提交过，写出把它从版本库移除但保留在硬盘上的命令。
