第 4 章 调试实战

预计 40 分钟·约 5,969 字·C 语言实战

写代码的时间大概三成，改 bug 的时间七成。这个比例我刚学 C 的时候不信，后来信了。更气人的是，有些 bug 不崩、不报错，只是算出来的数差一点。

调试不是玄学，是一套可以练的流程：先看报错，再缩小范围，再验证假设，最后修。这一章按这个顺序走，工具从 printf 到 Dev-C++ 再到 gdb。

4.1 报错信息怎么读#

编译器报错看着吓人，其实结构很固定：文件:行:列: 级别: 消息。先看第一条，不要从最后一条看。

C
#include <stdio.h>

int main(void) {
    int a = 1
    int b = 2;
    printf("%d\n", a + b);
    return 0;
}

用 gcc -std=c99 -Wall err.c -o err 编译，会得到：

TEXT
err.c: In function 'main':
err.c:5:5: error: expected ',' or ';' before 'int'
     int b = 2;
     ^
err.c:6:24: error: 'b' undeclared (first use in this function)

第一条说第 5 行的 int 前面缺了分号。可第 5 行本身没毛病，真正缺分号的是第 4 行末尾。报错行是「编译器发现问题的地方」，不一定是「问题所在的地方」。看到 expected ';'，先看上一行。

第二条 'b' undeclared 是第一条的连锁反应：b 的声明被上一行的错误吞掉了。所以修完第一条，后面可能自己消失。一上来就盯着最后一条改，往往越改越乱。

常见的报错按阶段分三类：

信息阶段常见原因
expected ',' or ';'编译上一行末尾少了分号
'x' undeclared编译拼错名字、没声明、超出作用域
implicit declaration of function编译没 include 对应头文件
undefined reference to 'foo'链接只有声明没有定义，或漏编译了 .c
multiple definition of 'x'链接定义写进了头文件
Segmentation fault运行指针或越界，编译器管不了

warning 也别跳过。-Wall 打开的警告里，uninitialized、implicit declaration、format 这几类经常是 bug 的前身。编译器的警告不是唠叨，是它见过太多人栽在同样的地方。

4.2 段错误的三大来源#

Segmentation fault 的意思是：你访问了一块不该访问的内存，操作系统把进程杀了。不是 C 语言杀的，也不是编译器杀的。

新手遇到的段错误，九成来自下面三种。代码里把野指针和悬垂指针拆成了两行，它们算同一类。

C
#include <stdio.h>
#include <stdlib.h>

int main(void) {
    int *p = NULL;
    // *p = 1;                  // 1. 空指针

    int a[3] = {1, 2, 3};
    // a[3] = 4;                // 2. 越界

    int *q;                     // 3. 野指针
    // *q = 5;

    int *r = malloc(sizeof(int));
    free(r);
    // *r = 6;                  // 4. 释放后继续用

    printf("%d\n", a[0]);
    return 0;
}

把注释一行一行打开，一次只开一个，观察程序怎么死。这段代码把危险行都注释了，直接编译只会得到 p 和 q 未使用的警告，不影响运行。

空指针：NULL 在大多数系统里就是地址 0，这个地址被操作系统特意留空，解引用一定崩。这是三种里最好查的，因为崩得干脆。

越界：a[3] 已经出了数组，但语法完全合法。它可能改掉隔壁的变量，可能读到垃圾值，也可能什么反应都没有。越得越远，越容易崩。越界最坏的结果不是崩溃，是没崩。

野指针和悬垂指针：野指针是没初始化的指针，里面是栈上的垃圾值；悬垂指针是 free 之后还接着用的指针，内存已经还给系统，地址却还留着。还有一种是返回局部变量的地址，函数一结束，那块栈空间就失效了。

为什么越界有时候不崩？因为那块内存可能刚好还属于你的进程，比如紧挨着的另一个变量。操作系统只拦「不属于这个进程」的地址，不拦「属于你但不该碰」的地址。于是 bug 变成「改 A 却影响了 B」，比直接崩溃难查十倍。

4.3 printf 插桩：最土但最快#

没有调试器的时候，printf 就是调试器。思路是二分：在可疑区间的中间打印一次，看程序走到哪、变量是多少，把范围砍一半，再砍一半。

C
#include <stdio.h>

int sum_array(int a[], int n) {
    int sum = 0;
    for (int i = 0; i < n; i++) {
        fprintf(stderr, "i=%d a[i]=%d sum=%d\n", i, a[i], sum);
        sum += a[i];
    }
    return sum;
}

int main(void) {
    int a[3] = {10, 20, 30};
    printf("sum = %d\n", sum_array(a, 3));
    return 0;
}
运行结果
i=0 a[i]=10 sum=0
i=1 a[i]=20 sum=10
i=2 a[i]=30 sum=30
sum = 60

三个技巧：

  • 打到 stderr，不要打到 stdout。stderr 默认不带缓冲区，程序崩溃前的内容不会丢；stdout 重定向到文件时是全缓冲，崩溃可能把最后几行吞掉。
  • 带上循环变量或阶段标记，不然一片输出分不清是哪一轮。
  • 打印变量的值，不要只打印「到这里了」。你要验证的是假设，不是刷存在感。

__LINE__ 是预定义宏，展开成当前行号；__func__ 是当前函数名，C99 才有。把它们拼进输出，日志会好读很多。

插桩完记得删，或者用 #ifdef DEBUG 包起来。交作业时满屏调试输出，助教的表情不会太好看。

4.4 完整案例：一个「差不多对」的平均分#

这是我这学期见过最像灵异事件的一个 bug。程序不崩，输出也有模有样，就是平均分比手算高了一点。

C
#include <stdio.h>

struct ScoreBook {
    int scores[5];
    int count;
};

int main(void) {
    struct ScoreBook book = {{80, 92, 76, 88, 95}, 5};
    int sum = 0;

    for (int i = 0; i <= book.count; i++) {
        sum += book.scores[i];
    }

    printf("总分 %d，平均 %.1f\n", sum, (double)sum / book.count);
    return 0;
}

手算：(80 + 92 + 76 + 88 + 95) / 5 = 431 / 5 = 86.2。程序输出：

运行结果
总分 436，平均 87.2

多了 5 分，平均正好多 1 分。5 从哪来的？

看循环条件：i <= book.count，count 是 5，所以 i 会取 0、1、2、3、4、5，一共六次。book.scores[5] 越界了。

更巧的是，结构体里 scores 后面紧挨着 count，scores[5] 的地址正好是 count 的地址，于是它读到了 5。总分多加了 5，平均多 1。

这不是巧合，是内存布局。换一台机器、换一个编译器，scores[5] 可能读到别的值，也可能直接崩。越界的表现不稳定，所以它难查。你不能靠「上次运行是对的」来证明这次也对。

4.5 用 Dev-C++ 断点看它#

图形调试器的好处是直观：变量值就在旁边，不用自己打印。

  1. 保存文件，确认当前是 Debug 配置（Dev-C++ 5.11 默认就是）。
  2. 在 sum += book.scores[i]; 这一行的行号左侧灰色区域点一下，出现红色圆点，断点就打上了。
  3. 按 F5 开始调试。如果它先停在 main 的第一行，再按一次 F5，就会跑到你设的断点。
  4. 停下来后，把鼠标悬在 i 上，或者在变量上右键选「添加查看」，把 i、sum、book.count 加进监视窗口。
  5. 按 F7 执行下一行（不进入函数），按 F8 进入函数。这里没有函数调用，F7 就够。
  6. 连着按 F7，看 i 从 0 走到 5。走到 5 的时候循环居然还在进，问题就露出来了。
  7. 在监视窗口里手动加 book.scores[5] 和 book.count，两个都是 5。到这一步，基本可以确定是 <= 写错了。
  8. 停止调试，改条件，重新编译。

断点不生效，通常是三个原因：编译时没生成调试信息（检查「工具 → 编译选项 → 代码生成/优化 → 产生调试信息」是不是 Yes）；改完代码没重新编译；运行的是别处的旧 exe。

快捷键也值得记一下：Dev-C++ 5.11 里 F5 是开始调试，F7 是下一行，F8 是进入函数。不同版本可能微调，记不住就直接看「调试」菜单，别硬背。

4.6 用 gdb 看同一个 bug#

gdb 是命令行调试器，Dev-C++ 的图形调试底层也是它。学会五六个命令，在任何 Linux 服务器上都能查问题。

编译时加 -g，然后启动：

Shell
gcc -g -std=c99 avg.c -o avg
gdb ./avg

进去以后是一串 (gdb) 提示符。最常用的命令：

  • break 位置：下断点，可以写 main、avg.c:13，也可以加条件 avg.c:13 if i == 5
  • run：从头运行，遇到断点停下
  • print 表达式：看变量，比如 print i、print book.scores[5]
  • next：执行下一行，不进入函数
  • continue：继续跑到下一个断点
  • bt：程序崩了以后看调用栈
  • quit：退出

针对 4.4 的程序，一次真实的会话大概是这样：

Shell
$ gcc -g -std=c99 avg.c -o avg
$ gdb ./avg
(gdb) break avg.c:13 if i == 5
Breakpoint 1 at 0x4015a6: file avg.c, line 13.
(gdb) run
Starting program: /home/you/avg

Breakpoint 1, main () at avg.c:13
13          sum += book.scores[i];
(gdb) print i
$1 = 5
(gdb) print book.count
$2 = 5
(gdb) print book.scores[5]
$3 = 5
(gdb) next
12          for (int i = 0; i <= book.count; i++) {
(gdb) print sum
$4 = 436
(gdb) bt
#0  main () at avg.c:12
(gdb) quit

在 Windows 上把 gdb ./avg 换成 gdb avg.exe，-o avg 生成的文件也带 .exe 后缀。

break avg.c:13 if i == 5 是条件断点，只在 i 等于 5 时停，省得你按五次 continue。print book.scores[5] 和 print book.count 输出一样，是因为它们指向同一块内存。

next 和 step 的区别：next 把函数调用当成一行执行完，step 会钻进去。查自己的 main 用 next，怀疑某个函数内部有问题用 step。

程序如果已经崩了，gdb 会停在出事那一行。先 bt 看调用栈，再 print 看局部变量。不想交互的话，一条命令也能拿到现场：gdb -batch -ex run -ex bt ./avg。

4.7 修好之后#

把 <= 改成 <：

C
#include <stdio.h>

struct ScoreBook {
    int scores[5];
    int count;
};

int main(void) {
    struct ScoreBook book = {{80, 92, 76, 88, 95}, 5};
    int sum = 0;

    for (int i = 0; i < book.count; i++) {
        sum += book.scores[i];
    }

    printf("总分 %d，平均 %.1f\n", sum, (double)sum / book.count);
    return 0;
}
运行结果
总分 431，平均 86.2

修完别急着交，做三件事：

  1. 用 -Wall 重新编译，确认没有新警告。
  2. 跑边界用例：空数组、只有一个元素、元素个数达到上限。很多 bug 只在边界出现。
  3. 想一想「这个错误还会在别的地方出现吗」，把 <= 和数组长度相关的循环全局搜一遍。

更稳的写法是让长度自己算出来，别手写 5：int n = sizeof(book.scores) / sizeof(book.scores[0]);。

循环条件用 i < n，取元素前确认 i >= 0 && i < n。调试时还可以加 assert(i >= 0 && i < n)，条件不成立就直接 abort，比越界后改坏别的变量好查。发布时用 -DNDEBUG 把 assert 关掉。

段错误不可怕，可怕的是它这次没崩。没崩的越界会悄悄改坏别的变量，让你在几百行外找 bug。所以看到「改 A 影响 B」，第一反应永远是查下标。

◆小结
  • 报错从第一条读，expected ';' 往往要看上一行；编译、链接、运行三个阶段要分清
  • 段错误三大来源：空指针、越界、野指针或悬垂指针
  • printf 插桩打印到 stderr，带上变量值；__LINE__ 和 __func__ 能标出位置
  • Dev-C++ 用 F5 调试、F7 下一行、F8 进入函数；gdb 用 run、break、print、next、continue、bt
  • 修完开 -Wall 跑边界用例，越界这种 bug 要顺藤摸瓜查同类循环
✎练习
  1. 判断下面四种写法分别属于哪类问题：int *p; *p = 1;、free(p); *p = 1;、int *p = NULL; *p = 1;、int a[3]; a[3] = 1;。可选类别：空指针、越界、野指针、悬垂指针。
  2. 写一个程序，读入 5 个整数存进 int a[5]，用 i <= 5 遍历并求和，运行观察结果；再用 printf 插桩打印每一轮的 i 和 a[i]，定位问题并修复。
  3. 用 gdb 给 4.4 的程序下条件断点 break avg.c:13 if i == 5，打印 i、book.count、book.scores[5] 和 sum，把会话过程记下来。
  4. 给 4.7 的循环加上 assert(i >= 0 && i < book.count)（记得 #include <assert.h>），分别用默认编译和 -DNDEBUG 编译运行，观察断言的行为。
