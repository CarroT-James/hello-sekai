第 16 课 项目：一个能测试的命令行工具

预计 35 分钟·约 7,694 字·Python

前面十五课的代码，基本都是「写完，跑一遍，看着对，收工」。

我也这么干过很久。改一行、手动点一遍、再改一行、再点一遍，一个下午就没了。更惨的是改完 A 功能，B 功能悄悄坏了，你三天后才发现。这一课把这两件事一起解决：用 argparse 把参数收干净，用 unittest 让机器替你点。

16.1 需求与结构#

做一个极简待办工具，四条命令：加一条、列出来、标完成、看统计。数据存 todo.json。

TEXT
todo/
  __init__.py
  core.py
  cli.py
tests/
  test_core.py

四个文件分工明确：

  • core.py 管数据和规则，不知道有命令行这回事
  • cli.py 管参数解析和读写文件
  • test_core.py 只测 core
  • __init__.py 让 todo 成为一个包

最关键的一条：core.py 绝对不许 import cli。依赖只能单向，cli 依赖 core。这样 core 才能被测试、被脚本、被将来的网页后端复用。

写的时候顺序反着来：先把 core.py 写完、测通，再写 cli.py。core 不依赖任何东西，可以边写边在交互式环境里试；cli 依赖 core，反过来就卡住。这个坑我踩过——先写界面后写逻辑，最后发现逻辑根本没法单独测，只能推倒重来。

16.2 核心逻辑：core.py#

这个文件里只有数据结构和规则，没有任何输入输出：

Python
"""核心逻辑，跟命令行、文件都无关。"""
from dataclasses import dataclass, field


@dataclass
class Task:
    title: str
    done: bool = False


@dataclass
class TodoList:
    tasks: list = field(default_factory=list)

    def add(self, title):
        title = title.strip()
        if not title:
            raise ValueError("待办内容不能为空")
        self.tasks.append(Task(title))
        return self.tasks[-1]

    def complete(self, index):
        if not 1 <= index <= len(self.tasks):
            raise IndexError(f"没有第 {index} 条待办")
        self.tasks[index - 1].done = True

    def pending(self):
        return [t for t in self.tasks if not t.done]

    def stats(self):
        total = len(self.tasks)
        finished = total - len(self.pending())
        return {"总数": total, "完成": finished, "未完成": total - finished}

Task 和 TodoList 都是 @dataclass，第 10 课 学的，这里正好用上：字段少、纯装数据，手写 __init__ 和 __repr__ 是浪费。

add 和 complete 都在做「守卫」：add 不许空内容，complete 不许越界。非法输入就在这里抛异常，别让它流到后面变成一条脏数据。守卫越靠前，后面要检查的地方越少。

注意这个文件里没有 print，也没有 open。不是洁癖，是为了能测。打印和读写文件都是副作用（除了算结果，还动了外面的东西），混进逻辑里，测试就得去抓屏幕输出、去造临时文件，麻烦十倍。

complete 用的是从 1 开始的下标，因为用户看到的是「第 1 条」。内部列表从 0 开始，转换在 self.tasks[index - 1] 这一下完成。让用户从 1 数，是命令行工具的惯例。

stats 里用 total - len(self.pending()) 算完成数，不再遍历一遍。这样「什么叫未完成」只有 pending 一处定义，将来加个「已归档」状态也只改它。

16.3 命令行：argparse#

命令行参数就是空格分开的几个词：todo add 买牛奶 里，todo 是程序，add 是子命令，买牛奶 是内容。argparse 帮你把这些词分好类，还顺手生成帮助页：

Python
"""命令行入口：解析参数，调用 core，读写文件。"""
import argparse
import json
from pathlib import Path

from todo.core import TodoList

DATA = Path("todo.json")


def load(path=DATA):
    todo = TodoList()
    if path.exists():
        data = json.loads(path.read_text(encoding="utf-8"))
        for item in data:
            task = todo.add(item["title"])
            task.done = item["done"]
    return todo


def save(todo, path=DATA):
    data = [{"title": t.title, "done": t.done} for t in todo.tasks]
    path.write_text(json.dumps(data, ensure_ascii=False, indent=2), encoding="utf-8")


def build_parser():
    parser = argparse.ArgumentParser(description="极简待办工具")
    sub = parser.add_subparsers(dest="command", required=True)

    add = sub.add_parser("add", help="加一条待办")
    add.add_argument("title", help="待办内容")

    sub.add_parser("list", help="列出全部待办")
    sub.add_parser("stats", help="看统计")

    done = sub.add_parser("done", help="把第几条标记为完成")
    done.add_argument("index", type=int)

    return parser


def main(argv=None):
    args = build_parser().parse_args(argv)
    todo = load()

    if args.command == "add":
        task = todo.add(args.title)
        save(todo)
        print(f"已添加：{task.title}")
    elif args.command == "list":
        if not todo.tasks:
            print("还没有待办。")
        for i, t in enumerate(todo.tasks, 1):
            mark = "x" if t.done else " "
            print(f"{i}. [{mark}] {t.title}")
    elif args.command == "done":
        todo.complete(args.index)
        save(todo)
        print(f"第 {args.index} 条已完成")
    elif args.command == "stats":
        print(todo.stats())


if __name__ == "__main__":
    main()

add_subparsers 让 todo add xxx 和 todo list 走不同分支，每个子命令有自己的参数。dest="command" 把用户敲的子命令名存进 args.command，下面的 if 就靠它分流。required=True 保证不敲子命令直接报错，不会静默什么都不做。

argparse 还会自动生成 --help，每个子命令都有自己的帮助页。上面那些 help="..." 就是给它用的，别人 todo add --help 一眼就知道要传什么参数。这部分文档不用另写。

add_argument("index", type=int) 里的 type=int 会自动把 "3" 转成 3，转不了就报错并打印用法。你不用自己 int(sys.argv[2])，也不用自己写 try。

main(argv=None) 那个参数是给测试留的口子。默认 None 表示读真实命令行，传 ["add", "测试"] 就能在测试里模拟一次调用，不用开子进程。不过它照样会读写真实的 todo.json——想彻底隔离，就得把文件路径也从参数传进来，那是下一步的事。

load 里复用 todo.add 再改 done，而不是直接造 Task(...)，这样空标题的脏数据会被同一套规则挡掉。

16.4 跑起来#

在项目根目录，按顺序敲：

Shell
python -m todo.cli add "买牛奶"
python -m todo.cli add "写作业"
python -m todo.cli list
python -m todo.cli done 1
python -m todo.cli stats
python -m todo.cli list
运行结果
$ python -m todo.cli add 买牛奶
已添加：买牛奶
$ python -m todo.cli add 写作业
已添加：写作业
$ python -m todo.cli list
1. [ ] 买牛奶
2. [ ] 写作业
$ python -m todo.cli done 1
第 1 条已完成
$ python -m todo.cli stats
{'总数': 2, '完成': 1, '未完成': 1}
$ python -m todo.cli list
1. [x] 买牛奶
2. [ ] 写作业

为什么是 python -m todo.cli 而不是 python todo/cli.py？因为 -m 会把当前目录放进模块搜索路径，from todo.core import TodoList 才找得到 todo 这个包。直接跑文件的话，搜索路径变成 todo/ 目录，import todo 立刻 ModuleNotFoundError。

if __name__ == "__main__": main() 还是老规矩：当脚本跑时执行，被 import 时不执行。测试里 from todo.cli import main 就不会顺手把程序跑起来。这一行在第 11 课 讲过，这里只是又用了一次。

数据存在 todo.json，关掉再开还在。用 json 而不是数据库，是因为只有几十条待办，json 足够，还方便你打开看看里面长什么样。

注意 todo.json 是相对路径，跟你在哪个目录运行有关。在项目根目录跑，文件就躺在根目录；cd 到别处再 python -m todo.cli，它会老老实实新建一个空文件，你会以为数据丢了。真做工具的话，把路径放到用户目录下更稳。

16.5 unittest：给代码上保险#

手动测试的问题是：这次点了、下次忘、改了 A 不知道 B 坏没坏。单元测试就是把「点一遍」写成代码，让机器每次替你点：

Python
import unittest

from todo.core import TodoList


class TestTodoList(unittest.TestCase):
    def setUp(self):
        self.todo = TodoList()
        self.todo.add("写作业")
        self.todo.add("买牛奶")

    def test_add_strips(self):
        task = self.todo.add("  跑步  ")
        self.assertEqual(task.title, "跑步")
        self.assertEqual(len(self.todo.tasks), 3)

    def test_add_empty(self):
        with self.assertRaises(ValueError):
            self.todo.add("   ")

    def test_complete(self):
        self.todo.complete(1)
        self.assertTrue(self.todo.tasks[0].done)
        self.assertEqual(self.todo.stats()["完成"], 1)

    def test_complete_out_of_range(self):
        with self.assertRaises(IndexError):
            self.todo.complete(99)

    def test_pending(self):
        self.todo.complete(2)
        self.assertEqual([t.title for t in self.todo.pending()], ["写作业"])


if __name__ == "__main__":
    unittest.main()

一个类继承 TestCase，每个以 test_ 开头的方法就是一个测试，方法名就是测试名。写了却没被执行的，多半是名字开头的 test_ 拼错了，或者缩进跑到了类外面。

setUp 在每个测试之前跑一次，用来准备干净的初始状态。上面每次都新建一个装了两条待办的 TodoList，所以测试之间互不影响——顺序换了、单独跑某一个，结果都一样。这一点很重要，测试不该依赖执行顺序。

三个断言最常用：assertEqual 判相等，assertTrue 判真假，assertRaises 判有没有抛异常（当上下文管理器用）。assertRaises 还有个好处：不抛异常它自己就失败，你不用担心「以为测了其实没测」。

测试写的不是「正常情况」，是「我担心的那种情况」。test_add_strips 特意传了带空格的 " 跑步 "，断言拿出来是 "跑步"。正常情况你手点一遍就过了，用不着写测试。

在项目根目录运行：

Shell
python -m unittest discover -s tests -v
运行结果
test_add_empty (test_core.TestTodoList.test_add_empty) ... ok
test_add_strips (test_core.TestTodoList.test_add_strips) ... ok
test_complete (test_core.TestTodoList.test_complete) ... ok
test_complete_out_of_range (test_core.TestTodoList.test_complete_out_of_range) ... ok
test_pending (test_core.TestTodoList.test_pending) ... ok

----------------------------------------------------------------------
Ran 5 tests in 0.000s

OK

discover -s tests 的意思是「去 tests 目录里找所有 test*.py 并运行」。-v 是 verbose，一个测试一行。后面那个耗时每次都不一样，0.000s 只是这台机器跑得快。

哪天你改坏了 add，这里立刻红一片，还告诉你哪个用例挂了。只想跑一个用例也行：python -m unittest tests.test_core.TestTodoList.test_add_empty，改哪儿测哪儿。比起手动点五遍，这就是十分钟换一下午。

16.6 打包发布：一句话版本#

想让别人敲 todo 就能用，而不是每次 python -m todo.cli，加一个 pyproject.toml：

TEXT
[project]
name = "todo"
version = "0.1.0"
dependencies = []

[project.scripts]
todo = "todo.cli:main"

然后在项目根目录 pip install -e .（末尾那个点指当前目录）。-e 是「可编辑安装」，装的是指向当前目录的链接，改代码不用重装。装完就能直接敲 todo add 买牛奶。

[project.scripts] 那行的意思是「生成一个叫 todo 的命令，执行 todo.cli 模块里的 main 函数」。这是 Python 打包的标准做法，pip、black、pytest 这些命令都是这么来的。

真要发布到 PyPI 让别人 pip install todo，还得注册账号、pip install build、python -m build、twine upload。这一步现在不用碰，知道有这回事就行。

这个装法还能干净卸载，pip uninstall todo 一句话，系统里不留垃圾。比「把脚本复制到某个目录、用的时候去那儿找」靠谱多了。

◆记忆点

能测的代码长什么样：不打印、不读文件、参数从外面传。把这三件事推到边缘，核心逻辑就是纯函数（同样的输入永远同样的输出，不碰外面），测试写起来两分钟一个。

◆小结
  • 项目分层：core 管逻辑不碰 IO，cli 管参数和文件，依赖单向
  • argparse 的 add_subparsers 做子命令，type=int 自动转换，main(argv=None) 方便测试
  • unittest 里 setUp 准备状态，test_ 开头的方法才被执行，assertRaises 测异常
  • 运行用 python -m 包.模块，路径才对；入口守在 if __name__ == "__main__": 后面
  • pyproject.toml 加 [project.scripts]，pip install -e . 之后就有自己的命令了
✎练习
  1. 给工具加 todo remove 2 命令，删掉第 2 条。先给 core.py 写 remove 方法，再补两个测试（正常删除、越界报错），最后才写 cli.py 的分支。
  2. 给 list 加一个 --done 参数，只显示已完成的。提示：add_argument("--done", action="store_true")，然后想清楚 args.done 为真为假时分别怎么过滤。
  3. 给 stats 加一个「完成率」字段，返回百分比（保留一位小数）。写测试的时候注意除零：一条待办都没有时该返回什么？
  4. 把 DATA 改成从环境变量读：os.environ.get("TODO_FILE", "todo.json")（记得在文件开头 import os）。写测试验证设置环境变量和不设置时，读的是不同文件。
